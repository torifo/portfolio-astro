  → **位置座標から機械的に都道府県を決める道は存在しない**
- `caption` のフィールド仕様に「Instagram API with **Facebook Login** only」との記載がある。
  → **要検証**。事実なら Facebook ページ連携が前提工程に入る

### 2.5 データエクスポート（採用する取得手段）

Instagram の「情報をエクスポート」（Accounts Center → Your information and permissions）で、全投稿のキャプションと画像を**トークン不要・アプリ不要・App Review 不要**で取得できる。

- `posts_1.json` に `title`（キャプション）、`creation_timestamp`、`media_metadata`（EXIF含む）
- **画像の実ファイルが同梱される**
- 既知の注意点:
  - **単一画像の投稿は post 直下に `title` / `creation_timestamp` が無く、キャプションは `media[0].title` にある**。カルーセルは post 直下にある

## 3. スコープ

### やること

- Instagram データエクスポートからの ingest パイプライン構築
- 地名 → 都道府県の解決パイプラインと辞書の初期構築（既存1,012件分）
- 都道府県別ページの静的生成
- 旅（トリップ）セクションと旅別ページ
- 既存 JourneySection の 47県データを JSON へ移設
- Instagram バナーのハンドル修正

### 軸は排他ではない — 1投稿が複数のページに出る

投稿は**独立した複数の軸**でタグ付けされ、各ページは自分の軸で絞り込むだけ。**軸をまたぐ重複表示は不具合ではなく仕様**である（本人決定）。

- 県をまたぐ投稿 → 関係する全県のページに出る
- 聖地巡礼タグのある投稿 → **都道府県ページにも聖地巡礼ページにも出る**
- 旅に属する投稿 → 県ページにも旅ページにも出る

したがって `posts.json` は `prefectures[]` / `trip` / `categories[]`（将来 `pilgrimage[]`）を並列に持ち、どこにも排他制約を置かない。

### タグの実測知見（取り込み時の正規化に必要）

126投稿の実キャプションから確認した事実。

- **不可視文字 U+2061（FUNCTION APPLICATION）がキャプション全体に散在する。** 除去しないとタグが正しく切れない
- タグの区切りは**半角スペース2個**が多い
- **略称と正式名称を両方タグ化する癖がある**（`#沖ツラ` と `#沖縄で好きになった子が方言すぎてツラすぎる`、`#与論島` `#ヨロン島` `#与論` `#ヨロン`）。別名の対応付けが自然にできる
- `#百合ヶ浜` の直後に付く `#ヶ浜` は、**本人が別プロジェクトで使うために意図的に付けているマーカー**である。パース不具合ではない（疑って検証した）

### 外部プロジェクト用タグ — 保存するが表示しない

`#ヶ浜` のように、**このポートフォリオとは無関係な別プロジェクトのために付けているタグ**が存在する。これらは地名としても被写体としても解決できないが、ノイズでもない。

扱いは次のとおり:

- **保存する** — 本人の別プロジェクトが参照する可能性があるため、`hashtags[]` には原文のまま残す
- **サイトには表示しない** — 訪問者にとっては意味不明なノイズになるため、タグ表示やハイライトの対象から外す
- 管理は `categories.json` 内の除外リスト（`role: "external"`）で行う

**どのタグがこの分類に当たるかは本人にしか分からない。** ingest は未知タグを一覧に出し、本人が「これは外部用」と印を付けられるようにする。初期値として `#ヶ浜` を登録する。

### タグの多義性 — 「地名でないタグ」は捨てない

実データのタグ419種（126投稿ぶん）には、地名以外が多く含まれる。これらはノイズではなく**別の軸の素材**である。

| タグの種類 | 例 | 使いどころ |
|---|---|---|
| 地名 | `#上高地` `#乳頭温泉郷` `#角館駅` | 都道府県の判定 |
| 旅グルーピング | `#新幹線セール2泊3日の梅雨シーズン秋田観光旅` | 旅セクション |
| **料理・グルメ** | `#秋田プリン` `#一丸鮨` `#沖縄料理` `#純和鶏あさひ塩こしょう焼` | **県ページのハイライト**（本フェーズ） |
| **作品名** | `#陰の実力者になりたくて2期` | **聖地巡礼**（別セッション） |
| 被写体・その他 | `#蛍` `#こまち` `#グラデーションが綺麗すぎる` | カテゴリ、または未使用 |

**料理ハイライトの実現方法**: 料理タグの多くは店名・商品名（`#一丸鮨`）でオントロジーには載らないため、Wikidata だけでは同定しきれない。次の合わせ技にする。

1. パターン（`〜料理` `〜グルメ` `〜そば` `〜寿司` など）
2. Wikidata の日本料理・郷土料理・菓子クラス
3. `categories.json` への人手登録
4. LLM の任意支援（他と同じく候補を出すだけ）

なお、分類が難しければ**「その県の投稿に頻出する、地名でないタグ」を出すだけでもハイライトとして成立する**。完全な分類を前提条件にしない。

### 将来の拡張（別セッションで扱う）

**聖地巡礼セクション。** 実データに `#陰の実力者になりたくて2期` のようなアニメ作品名タグが含まれており、これは地名ではないがノイズでもない。作品名タグと地名タグが同居する投稿は聖地巡礼の記録であり、**都道府県・旅に次ぐ第3の軸**になりうる。

そのため本フェーズで**必ず守る前提がある**:

> **ハッシュタグは解決できたものだけでなく、全件を原文のまま `posts.json` の `hashtags[]` に保存する。**

解決できなかったタグを捨てると、後から聖地巡礼を作るときに**取り込みからやり直しになる**。作品名のオントロジー（Wikidata のアニメ作品）は別途必要になるが、それは後から足せる。捨てたデータは後から足せない。

### やらないこと（今回のスコープ外）

- Instagram API による自動増分取り込み（**後続フェーズ**。設計だけ用意し、実装は分ける）
- 訪問していない県のコンテンツ拡充（本人が「今後配置するとアナウンスするか別サイトを作る」と判断）
- 地図SVGによるビジュアル表現

## 4. アーキテクチャ

### 4.1 基本方針: ingest をビルドから切り離す

```
[Mac] npm run journey:ingest
   ↓ エクスポートを読む → 解決 → サムネ生成
[repo] src/data/journey/*.json + public/journey/thumbs/*.webp をコミット
   ↓ git push main
[CI] npm run build   ← Instagram にも LLM にも一切触れない
```

**CI は純粋なビルドのまま保つ。** ビルド時に外部APIを叩くと、トークン失効やレート制限が「サイトがビルドできない」に直結する。既存の microCMS とは方針が異なるが、1,012件＋トークン期限という条件では切り離す方が安全。

### 4.2 外部依存を「任意レイヤ」に統一する

本設計の中心原則。ユーザーの明示的な要求:

> llm-gatewayは必ず使えるかはわからない不安定な方法だと思って。強いけどそれを必ず使わないと失敗するようでは設計として困る
> 使ってもいいか、それありきの設計だと困るってこと。いつか使えなくなる可能性があったありの予防で

したがって、**不安定な外部依存はすべて「あれば便利」な位置に置き、失っても壊れない**ようにする。

| 依存先 | 位置づけ | 失われたときの挙動 |
|---|---|---|
| LLM（jai-gw / Codex / VPS gateway） | **任意**。辞書の起草者であって判定器ではない | 既に育った辞書で判定が続く。新規の未知地名が未解決に残るだけ |
| Instagram API | **任意**。増分取り込みの便利手段 | データエクスポートで更新を継続できる |
| VPS | **土台にしてよい** | ポートフォリオ本体が動いているインフラなので、これが死ぬときはサイトも死んでいる。LLM Gateway（Claude Max サブスク依存）とはリスクのカテゴリが違う |

## 5. 都道府県の解決パイプライン

### 5.1 層構造（上が優先）

| 層 | 手段 | 例 |
|---|---|---|
| **L0** | `overrides.json` — 人間の最終決定 | 常に勝つ。再 ingest・辞書更新でも上書きされない。「分類を空にする」指定も可能 |
| **L1** | EXIF の GPS 座標（**取得できた投稿のみ**） | 緯度経度 → 県。決定的 |
| **L2** | 県名の直接一致 | `#長野県` → 長野。47県＋別名表。**長いタグ内の部分一致も許可**（`#…秋田観光旅` → 秋田） |
| **L3** | `places.json` — **確定辞書**（小さい・人が育てる） | `上高地`→長野 / `乳頭温泉郷`→秋田 / `HANABIYORI`→東京 |
| **L4** | **オントロジー**（大きい・機械生成の参照表） | Wikidata 由来の全国地名表。候補が1件に定まれば採用し、`places.json` に昇格させる |
| **L5** | 旅グループ継承 | 同じ旅タグ内で解決済みが過半なら継承。信頼度を一段下げて記録 |
| **L6** | **LLM（任意・オフ可）** | 未解決語、またはオントロジーで候補が絞れなかった語について**辞書エントリ候補**を `suggestions.json` に出すだけ。人が承認して `places.json` に昇格させて初めて判定に効く |
| 終端 | `unresolved` | 県ページには出さない。旅ページ・投稿一覧には「地域未分類」として出す |

**LLM の出番は2箇所だけ**である。①オントロジーに無い語、②オントロジーで候補が複数あり絞れない語。それ以外は JSON を引くだけで決まる。承認された結果は `places.json` に入り、**同じ語で二度と LLM を呼ばない**。

### 5.2 核心となる性質

**判定は `raw + 辞書 + override` の純関数**であり、ingest のたびに全件を再計算する。

- LLM の出力が直接サイトに載ることはない（必ず辞書を経由する）
- 非決定性は「辞書を起草した一回きり」に封じ込められる
- LLM が使えなくなっても、育った辞書でサイトは動き続ける

### 5.3 誤爆対策

L2 の部分一致は誤爆しやすいため stoplist を持つ。例: `大分類`（→大分ではない）、`三重奏`（→三重ではない）、`宮城野`（→宮城とは限らない）、`奈良漬`、`京都風`。

完全一致・最長一致を優先し、単純な部分文字列一致だけで県を確定しない。同名地名・県境の施設は候補を複数保持し、確定させずに `unresolved` 扱いにして人間の判断に回す。

### 5.4 複数県の扱い — 「またがり」と「同名異所」を必ず区別する

1投稿が複数県にまたがることがあるので `prefectures` は**配列**とする。ただし「県が複数ついた」状態には**性質の違う2種類**があり、混同すると誤りが正しい結果として公開されてしまう。

| 種類 | 検出方法 | 例 | 扱い |
|---|---|---|---|
| **またがり** | **同一 QID** が複数の市区町村に属する | よみうりランド（東京・神奈川）、白神山地（青森・秋田） | ✅ 正しい。**全県のページに重複表示する**（本人決定） |
| **同名異所** | **異なる QID** が同じラベルを持つ | 厳島神社（広島・北海道・兵庫・山口・京都・福島・愛媛…） | ⚠️ 本来どれか1つ。確定させず L6（LLM／人）へ回す |

QID が同じか違うかで機械的に判別できる。**この区別が無いと、解決の誤りが「県境をまたぐ場所」として正当化されてしまう**ため、オントロジーの索引を作る段階で必ず判定する。

同名異所の絞り込みには Wikidata のサイトリンク数（知名度の代理指標）を使う。差が大きければ自動採用し、拮抗していれば曖昧のまま残す。

### 5.5 遡りすぎの禁止

所在地は **P131 を1ホップだけ**辿り、行き先が市区町村テーブルに載っていることを要求する。

再帰的に遡る（`P131*`）と国立公園や地方といった広域エンティティを経由してしまい、実測で **「乳頭温泉郷 → 東北6県」**（正解は秋田県のみ）という誤りが出た。これは「またがり」ではなく純粋な解決の誤りであり、§5.4 の区別だけでは防げない。浅く辿ることが唯一の対策。

### 5.6 visited と「投稿がある」は別概念

投稿が無い県を未訪問に書き換えてはならない。`visited` は本人が手で管理するフラグであり、投稿数とは独立に持つ。

## 6. データモデル

すべて UTF-8 JSON、`src/data/journey/` 配下、git 管理。**生成されるファイルと人間が編集するファイルを分ける**。

| ファイル | 種別 | 内容 |
|---|---|---|
| `prefectures.json` | 人間 | 47県マスタ。`code` / `name` / `en` / `slug` / `region` / `gradient` / `visited` / `note`。**現在 `.astro` にベタ書きの内容をここへ移設**し、既存の `note` は維持する |
| `posts.json` | 生成 | `id` / `permalink` / `date` / `caption` / `hashtags[]` / `mediaType` / `thumb` / `prefectures[]` / `trip` / `categories[]` / `resolution{method, confidence}` |
| `trips.json` | 生成＋人間 | `slug` / `tag`（原文のまま保存） / `title`（表示名・手動上書き可） / `dateRange` / `prefectures[]` / `postIds[]` |
| `places.json` | **資産** | 確定辞書。`name` / `aliases[]` / `prefCodes[]` / `kind` / `source`（根拠） / `verifiedAt` |
| `categories.json` | 人間 | 地名ではない被写体タグの対応。`#蛍`→自然観察 / `#新幹線`→公共交通 など |

`kind`（場所の種別）を `places.json` 側に持たせることで、**1エントリから県とカテゴリの両方が出る**。`categories.json` は地名ではないタグだけを受け持てばよくなり、辞書の重複が消える。種別→カテゴリの対応は `scripts/ontology/kinds.py` の `CATEGORY_OF_KIND` に持つ。

**注意**: 長い旅タグが category 語を含むことがある（`#新幹線セール2泊3日の梅雨シーズン秋田観光旅` は「新幹線」を含む）。旅タグと判定したものは**カテゴリ抽出の対象から外す**。

### オントロジー（ingest 専用・ブラウザには配信しない）

`data/ontology/` 配下。Wikidata（CC0）から機械生成する参照表で、`src/data/journey/` とは役割が違う。

| ファイル | 内容 |
|---|---|
| `prefectures.json` | 47都道府県。団体コード2桁を正とする |
| `municipalities.json` | 1,979市区町村。所在地を遡るときの停止点 |
| `places.json` | 全国の地名。`name` / `aliases[]` / `prefCodes[]` / `kinds[]` / `sitelinks` |
| `kinds.json` | 採用した種別クラスの一覧（実データで存在を確認したもの） |

ビルドスクリプトは `scripts/ontology/`。実際に構築して判明した落とし穴を以下に残す。**いずれも推測ではなく実行結果から得たもの**で、作り直すときに同じ失敗を繰り返さないために記録する。

| 落とし穴 | 症状 | 対処 |
|---|---|---|
| クラスIDの決め打ち | 温泉のつもりで `Q179700` を使ったら**像**が返ってきた | 検索APIと件数計測で実在を確認してから採用する。`kinds.py` の値はすべて検証済み |
| 「県の直下＝市区町村」という仮定 | 県に直接ぶら下がる建物や山まで拾い **25,656件**になった | 全国地方公共団体コード（`P429`）を持つことを条件にする。1,979件に収まる |
| 県名ラベルでの突き合わせ | **東京府**（歴史上の行政区画）が混入し県が48種類になった | 団体コード先頭2桁を正とする。必ず 01〜47 に収まる |
| `P131*` の無制限な遡り | 乳頭温泉郷が東北6県にヒット。応答が **143MB** になり JSON 解析も破綻 | 1ホップに限定し、行き先を市区町村テーブルに限る |
| 種別の一括カウント | `P279*` × 60クラスで Wikidata の60秒制限に当たり 504 | 市区町村を起点に県ごとへ分割し、1クエリ40市区町村に抑える |
| 日本語ラベルの欠損 | 無名の山が `Q31499258` のまま大量に混入 | `rdfs:label` の `ja` を必須にする |
| 種別ノイズ | 小学校1919・町丁1566・道路1205 などが上位を占める | 旅に関係する種別の許可リストで絞る |

### 実測した解決率（2026-09-11・HTML版エクスポートの126投稿で検証）

構築したオントロジーは **98,320件・11.7MB・索引語88,801語**（うち県境をまたぐ実体886件）。実タグで測った結果:

| 指標 | 値 |
|---|---|
| **投稿単位で県が決まった** | **115 / 126（91.3%）— LLM 呼び出しゼロ** |
| 未解決 | 11件（8.7%） |
| 内訳 | 一意62／県名一致21／一意＋知名度8／知名度のみ5 |

タグ単位の命中率は419種中62種（14.8%）だが、これは分母に料理・感想・作品名など地名でないタグを全部含むため、**評価指標として適切ではない**。1投稿に平均6タグあり、1つ当たれば県が決まるので、投稿単位の91.3%が実力である。

正しく解けた例（かつて `P131*` で失敗した事例を含む）:

```
#乳頭温泉郷    -> 秋田県（温泉）          ← P131* では東北6県に誤爆していた
#よみうりランド  -> 東京都/神奈川県（遊園地） ← 県境をまたぐ実体として正しい
#与論島       -> 鹿児島県（島）
#スパリゾートハワイアンズ -> 福島県
```

**曖昧判定の改良点（実測で判明）**: `#千秋公園` は「千秋公園」と「久保田城」の2候補が出るが**どちらも秋田県**なので実は曖昧ではない。**候補が県で割れたときだけ曖昧とする**。`#富士山` は茨城・山梨/静岡・長野の3候補に割れるが、サイトリンク数の差で本命が確定する。

**未解決11件を減らす手立て（実装フェーズで対応）**: 未解決投稿はほぼ全て「同じ旅の他の投稿は解決できている」ケースだった。

1. **市区町村名の接尾辞を落とした別名を索引に追加** — `横須賀市` → `横須賀` で `#横須賀` が引ける
2. **旅タグ内の地名部分一致** — `#トーマス列車本栖湖経由富士芝桜祭り参戦旅` から `本栖湖`（山梨）を取る
3. **旅グループ継承（L5）** — 同じ旅タグの他投稿から継承する

Wikidata 自体のデータ誤りも一定数ある（実測で「利根川」が長野県の市区町村に紐付いていた）。**オントロジーは確定辞書ではなく候補源**であり、`places.json` と `overrides.json` が最終的な正である、という層構造がここでも効く。
| `overrides.json` | 人間 | 投稿ID別の県・旅・カテゴリ訂正、非表示指定、訂正理由 |
| `suggestions.json` | 生成 | LLM が出した未承認の辞書候補 |
| `manifest.json` | 生成 | `schemaVersion` / スナップショットID / 取り込み日時 / 件数 / 辞書バージョン |

### 画像

`public/journey/thumbs/<id>.webp`（480px・q70）。ingest 時に縮小して**リポジトリにコミットする**。

- `media_url` は失効し得るためホットリンクしない
- エクスポート同梱の原本から生成するので、Meta のキャッシュポリシー上の懸念も回避できる
- 概算 25KB × 1,012 ≒ **25〜40MB**。上限を決めて超えたら別リポ or VPS 配信へ移す

### 旅タグの判定規則

「一定文字数以上」または「`旅` `編` `日目` 等の語を含む」タグを旅タグ候補とし、初回に候補一覧から人間が登録する。長さだけで自動確定しない。別表記は同じ旅IDへ統合できるようにする。

**投稿日時と旅行日は区別する。** 旅行日が不明な場合は「投稿期間」として表示する。

## 8. 既存1,012件のバックフィル手順

**一度きりの「辞書を育てる作業」**であり、「1,012件を分類する作業」ではない。

1. JSON形式のエクスポートを取得し `~/dev/data/instagram/<YYYY-MM-DD>/` に展開する
2. `posts_1.json` からキャプション・タグ・日付・画像パスを抽出して正規化する
3. EXIF に GPS があるか確認する（L1 が使えるかの判定）
4. L0〜L4 の決定的処理を全件に適用する
5. 未解決分について、**地名を重複排除してから** LLM に辞書候補を起草させる
   - 担当: **jai-gw（astra）→ 失敗したら Codex にフォールバック**（本人指示）
   - VPS の llm-gateway は使わない（本人指示）
   - **全投稿を LLM に送る設計にはしない。** 未知の地名だけを対象にする
6. 候補を人間がレビューして `places.json` / `overrides.json` に確定させる
7. 残った未解決は `unresolved` のまま公開する

**分類100%の達成を公開開始の条件にしない。** これが継続運用の要点。

## 9. 増分更新とトークン戦略（後続フェーズ）

### 手段の優先順位

1. **Instagram API による増分取り込み**（実装すれば最も楽）
   - 既知IDに当たるまで新しい順に取得
   - トークンは VPS の systemd timer で**週1リフレッシュ**（有効期限60日に対し週1なら、VPS が数週間落ちても間に合う）。llm-gateway で同じ仕組みの前例がある
   - 残日数を監視して閾値割れで通知（llm-gateway の `/health` が `token_days_left` を出しているのと同じパターン）
2. **データエクスポートの取り直し**（恒久フォールバック）
   - API が完全に使えなくなっても、これで更新を継続できる

### トークンが切れてもサイトは壊れない

コミット済みのデータで動き続け、ingest が失敗するだけ。復旧は OAuth のやり直し、または 2. のエクスポート。

設計書の「調査で確定した事実」のうち、**JSON版エクスポートの実データで覆ったもの**を
ここに記録する。上の本文はHTML版エクスポート（991MB・1年分）だけを見て書いたもので、
JSON版とは中身が違った。

## 覆った事実

| 本文の記述 | JSON版での実測 |
|---|---|
| エクスポートの緯度経度は126件中2件（1.6%）。GPS は県判定に使えない | **943/1013（93.1%）に EXIF の緯度経度がある。** HTML版が EXIF を落としていただけだった |
| キャプションは `media[0].title` にある | `label_values` の `キャプション` に明示的に入る。post直下に `緯度`/`経度` ラベルもある |
| キャプション先頭の日付は41% | **90%（912/1013）。** `2025年6月17日` 形式が461件あり、`YYYY-MM-DD` しか見ていなかったため取りこぼしていた |

## 日付の規則（本人の確認済み）

> 投稿に入れてる日付を使用して。投稿日時は全く意味ない。投稿日時がキャプションにない時だけ当日に投稿しているってことです。

- キャプション先頭に日付があれば、それが撮影日（後追い投稿）
- 無ければ当日投稿なので、アップロード日時が撮影日
- これで日付は100%埋まる。実測でも、キャプション日付を持つ912件は**全件が1日以上ずれ、同日は0件**であり、規則と整合する
- `2025年6月`のように日が無いものは月初に寄せ、`date_precision: "month"` を残す（27件）

## GPS とタグが食い違ったときの扱い

109件で食い違う。実例を読むと **GPSが正しい側が多数**だった。

- 記念艦「三笠」（横須賀）にタグ `#三笠` → オントロジーが北海道三笠市と誤判定。GPSが正
- USJ の投稿にタグ `#東京` → GPSが大阪で正
- 舞浜（千葉）の投稿にタグ `#東京ディズニー` → GPSが正
- 一方「帰りの高速バス」「ツアー特製お弁当」は撮影地が東京で、主題は旅先

本人の判断で **GPS優先（`--policy gps`）を既定**とし、食い違いは `conflicts.json` に
書き出して `overrides.json` で個別に裁定する。

**GPSが壊れている実例もある**: 寒風山（男鹿市・秋田県）の投稿の EXIF が山形県を指していた
（約200km南）。`overrides.json` で秋田に戻している。

## Instagram の投稿リンク

**エクスポートから permalink は取れない。** media id からショートコードを計算する方法も使えない。
「いいねした投稿」に自分の投稿が3件混ざっていたので、それで検証した:

| ショートコード | が表す pk | エクスポートの fbid | 比 |
|---|---|---|---|
| `DB_fXk8z-lR` | 3494649795527567697 | 17854470537300174 | 195.7 |
| `CxklREtvd80` | 3198845536354295604 | 18044896351503853 | 177.3 |
| `Cxr3BeoPXlv` | 3200893954341828975 | 17997653654133540 | 177.9 |

差も比も一致しない。**別系統の識別子**であり、計算では導けない。
個別投稿へのリンクは Instagram API の `permalink` フィールドで埋める
（`scripts/ingest/fetch_permalinks.py`）。埋まるまではプロフィールへ落ちる。

なお**キャプションの完全一致での突き合わせは3件とも成功**したので、
APIの `id` がエクスポートの `fbid` と違っていても紐付けられる。

### 結果（2026-09-12 取得済み）

```
API から 1013 件
  id で一致        : 1013
  キャプションで一致: 0
  結べなかった      : 0
→ data/journey/permalinks.json: 1013 / 1013 件 (100.0%)
```

**Graph API の `id` はエクスポートの `fbid` と同一だった**（ショートコードの元になる
内部 pk とは別系統、という判定はそのまま）。キャプション突き合わせは出番がなかったが、
ID体系が変わったときの保険として残す。

取得の前提として、Instagram アカウントをアプリの **Instagramテスター**として登録し、
本人が Instagram 側で承認する必要がある。これを飛ばすと OAuth が
`開発者の役割が不十分です` で失敗する。Webhook のコールバックURL、
ビジネスログインのリダイレクトURI、アプリレビューはいずれも不要
（ダッシュボードで手動生成したトークンを使い、自分のアカウントだけを読むため）。

トークンは `~/dev/.env.dev`（リポジトリ外・600）に置く。60日で失効するが、
`permalinks.json` に書き込んだ後はビルドが参照しないのでサイトは壊れない。


結果として **L6 の LLM は一度も呼ばずに 100% に到達した**。判定はすべて
`raw + 辞書 + override` の純関数の中で閉じている。

指定は記憶に頼ったものなので確度は一様ではない。`overrides.json` の該当IDを
直せば再ビルドで反映される。タグから再利用できるもの（`#初狩PA` `#こもれびの道`
`#カワゼミハウス` `#RestHouseLUE`）は `gazetteer.json` に入れ、以後同じタグが
来たら自動で解決するようにした。チェーン店のタグ（ロイヤルホスト、
ラ・メゾン アンソレイユターブル）は店舗ごとに県が変わるため辞書には入れていない。
